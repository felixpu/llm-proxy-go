# ADR-0001: 熔断器（Circuit Breaker）设计

日期：2026-03-04
状态：已实施

## 背景
在 LLM 代理服务中，上游 API 端点可能因为各种原因（网络故障、服务过载、配置错误等）出现故障。如果没有熔断机制，系统会持续向故障端点发送请求，导致：
1. 资源浪费（无效的网络请求和等待时间）
2. 用户体验下降（请求超时、错误率上升）
3. 级联故障（故障端点拖累整个系统）

需要一个智能的熔断器机制来自动检测和隔离故障端点，并在端点恢复后自动重新启用。

## 决策
实现基于状态机的熔断器（Circuit Breaker）模式，集成到健康检查器（HealthChecker）中：

### 核心组件
1. **状态机**：Closed（正常）→ Open（熔断）→ Half-Open（试探）→ Closed
2. **错误分类**：区分临时错误（网络超时）和永久错误（认证失败）
3. **自适应阈值**：根据错误率和连续失败次数触发熔断
4. **自动恢复**：Half-Open 状态下试探性发送请求，成功后恢复

### 关键参数
- 失败阈值：连续 3 次失败或错误率 > 50%
- 熔断时长：30 秒（可配置）
- 试探请求：Half-Open 状态下允许 1 个请求通过

### 集成点
- `internal/service/health_checker.go`：熔断器逻辑
- `internal/service/endpoint_store.go`：端点状态管理
- `internal/service/load_balancer.go`：跳过熔断端点

## 理由
1. **提升系统稳定性**：快速隔离故障端点，避免级联故障
2. **改善用户体验**：减少无效请求，降低延迟
3. **资源优化**：避免向故障端点发送请求，节省网络和计算资源
4. **自动恢复**：无需人工干预，系统自动检测端点恢复

## 考虑的替代方案

### 方案 1：简单的重试机制
- 优点：实现简单
- 缺点：无法快速隔离故障端点，会持续浪费资源

### 方案 2：基于时间的禁用
- 优点：实现简单，固定时间后重新启用
- 缺点：无法根据实际情况动态调整，可能过早或过晚恢复

### 方案 3：外部监控系统
- 优点：集中管理，可视化
- 缺点：增加系统复杂度，依赖外部服务

## 后果

### 正面影响
- 系统稳定性显著提升
- 故障端点自动隔离，减少用户感知的错误
- 资源利用率提高
- 自动恢复机制减少运维负担

### 负面影响
- 增加代码复杂度（状态机管理）
- 需要仔细调优参数（阈值、熔断时长）
- 可能出现误判（短暂网络抖动导致熔断）

### 风险
- 参数配置不当可能导致过于敏感或不敏感
- Half-Open 状态下的试探请求可能失败，延长恢复时间
- 需要充分测试各种故障场景
